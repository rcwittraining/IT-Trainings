1Requirements & design principles

This blueprint assumes a typical enterprise profile. Adjust the numbers, but keep the principles: every component that users must touch on the logon path exists in both sites, and no single device, server, database or WAN link can take the service down.

ScenarioAround 3,000 concurrent users: pooled desktops, published line-of-business applications and a small pool of persistent desktops for power users.
SitesSite A (primary data centre) and Site B (secondary data centre), roughly 40 km apart, connected by two diverse metro fibre paths with an RTT of about 2–4 ms between them.
TargetsRTO ≤ 15 minutes for a full site failure, RPO ≈ 0 for the Site database, no planned-downtime window needed for patching individual components, and zero user-visible impact for any single server or appliance failure.
UsersMostly on the corporate LAN split across both sites, plus roughly 15% remote users entering through Citrix Gateway.

Design principles

  • Failure domains, not just redundancy. Two of everything is not enough if both copies share a power feed, an uplink or a rack. Each site is a full failure domain; inside each site, pair members sit on separate hosts, storage and power.
  • Protect the logon path end to end. A user who cannot reach DNS, ADC, StoreFront, a controller, or the Site database cannot start work. Every hop on that path is load-balanced and duplicated.
  • Protect running sessions separately. Session Reliability and client auto-reconnect absorb network blips; capacity headroom and machine catalogs in both sites absorb host and site failures.
  • Fail over automatically where it is safe, deliberately where it is not. ADC HA, SQL Always On and GSLB health checks are automatic. Declaring a full site dead is a deliberate human decision, executed against a written runbook.
  • Design for the failure you fear, then test it. If a failure mode has never been simulated, assume it will not work the way the diagram says. Section 14 turns every arrow in the design into a test case.
Define “site failure” before you design for it

A “site failure” means different things to different teams: total power loss, core switch failure, WAN isolation (site alive but unreachable), or a ransomware event. This design treats total loss of Site A as the governing case. WAN-isolation cases (a site up but cut off) are covered in the failover matrix in section 11 because they need different handling — you must not run both halves of a split-brain environment against one database.

Recommendation for this blueprint

For two metro data centres 40 km apart with 2–4 ms RTT, Pattern A — one stretched CVAD site — gives the best blend of resilience and operational simplicity, and it is what the rest of this article designs in detail. If your sites are hundreds of kilometres apart or owned by different operational teams, use Pattern B (or C) and apply sections 3–6, 9 and 11–15 unchanged; they are pattern-independent.

4Edge layer: a Citrix ADC high-availability pair per site

Citrix ADC (formerly NetScaler) is the front door: it terminates TLS, load-balances StoreFront, fronts Citrix Gateway, and hosts the health monitors that GSLB uses. Design one HA pair per site, not one pair stretched across sites.

Per-site HA pair

  • Two appliances in active/standby HA on the same Layer-2 segment (hardware MPX, virtual VPX, or SDX-hosted). Keep the pair in the same DC: stretched HA across 40 km adds failover complexity without adding resilience — GSLB already handles the site level.
  • Independent Network Configuration (INC) so the standby node keeps its own server-side IP configuration; a failover then needs no routing changes upstream.
  • Dedicated NSIP per node plus a shared SNIP for server-side traffic; management access only through the NSIP and jump hosts, never through the data path.
  • Separate failure domains: the two nodes on different hypervisors/chassis, power feeds and uplink switches. An ADC pair sharing one switch stack is a single point of failure wearing a costume.
  • Identical configuration, licensed capacity and firmware on both nodes. Keep configurations in a versioned backup exported after every change; HA sync hides configuration drift until the day it matters.

Sizing the ADC platform

Size on three numbers: peak concurrent ICA/HDX connections through Gateway, SSL transactions per second at logon bursts (09:00 Monday is the real test), and total throughput with room to double. A single ADC node must be able to carry the full site load alone — HA capacity is not a license to run at 95% on the active node.

5GSLB & DNS: steering users between sites

Users know exactly one name: gateway.corp.example for remote access and a matching internal name for LAN users. Global Server Load Balancing on the Citrix ADC decides which site answers, based on health first and proximity second.

Design decisions

  • Active/active steering during normal operations. Both sites serve users in steady state (proximity/RTT-based method sends Site A LAN users to Site A and Site B LAN users to Site B). Capacity is used efficiently, and “failover” is already happening every day at small scale.
  • Health before proximity. Each GSLB service is bound to a monitor that performs a real HTTPS check against the site’s Gateway/StoreFront path. A site whose logon path is broken stops receiving new users automatically.
  • DNS TTL of 60 seconds on the GSLB records, so steering changes take effect quickly; keep the appliance’s DNS retry/timeout settings consistent with your corporate resolvers.
  • Remote users (Gateway FQDN): delegated to or answered by the ADC’s GSLB AD (Authoritative DNS) or via CNAME to the GSLB name.
  • Internal users (StoreFront base URL): resolve the StoreFront FQDN through AD-integrated DNS with DNS policies or subnet-based records so each site’s clients reach their local StoreFront VIP. Internal traffic should never be forced across the inter-site link to log on.
What GSLB does and does not move

GSLB steers new connections. It does not move established ICA sessions, and it does not “fail over” a user mid-session — that job belongs to Session Reliability, client auto-reconnect and capacity in the surviving site (sections 5 and 10). Set that expectation with stakeholders early: DNS-based failover means a brief reconnection window of one to two TTL periods during a site event.

Failover behaviour to expect

  • Single ADC node failure: HA failover in seconds; the VIP does not change; users see nothing.
  • Site A outage: monitors fail the GSLB services; new DNS answers point to Site B within ~1–2 minutes; clients retry and land on Site B. Existing sessions on Site A VDAs drop and users re-launch into Site B capacity.
  • WAN isolation of Site A (site up, link down): Site A keeps serving its own LAN users locally; GSLB stops sending remote users there. Do not declare full site failover for a WAN-only event — see the matrix in section 11.

6Citrix Gateway & remote access

Citrix Gateway runs on each site’s ADC pair and gives remote users the same StoreFront experience as LAN users, with HDX tunneled over TLS 443.

  • ICA proxy mode with SSL bridge: the ADC validates the launch ticket against a Delivery Controller (STA) and then brokers the ICA/HDX connection to the VDA.
  • Register controllers from both sites as STAs on both Gateways, and configure the same STA list in StoreFront. A launch ticket issued by a Site A controller can then be validated by Site B’s Gateway during a steering change, avoiding spurious “ticket cannot be validated” errors while both sites are alive.
  • Session Reliability on (TCP 2598 inside the SSL session): short network blips freeze the screen instead of dropping the session, and the session resumes without a re-launch.
  • Client auto-reconnect with a bounded retry count: if the connection really dies, the Workspace app re-establishes through whichever site GSLB now serves — this is the mechanism that makes a site failover feel like a hiccup rather than an outage for remote users.
  • Authentication: nFactor flow with MFA (RADIUS to your NPS/MFA platform or SAML to the IdP). Apply endpoint analysis (EPA) or conditional posture checks where policy requires them.
  • Session limits and timeout policies tuned per delivery group so a single account cannot exhaust pooled capacity from outside.
If a site dies, its sessions die with it

There is no such thing as live-migrating an ICA session from a VDA in Site A to a VDA in Site B. Sessions that were running on failed hardware are gone. Resilience for remote users therefore means: quick DNS steering + auto-reconnect + guaranteed capacity in the surviving site. Budget that capacity (section 10) or the failover will be technically perfect and operationally useless.

7StoreFront layer

StoreFront is the most sensitive hop on the logon path: enumeration, authentication hand-off, subscription store and launch tickets all live here. The resilient pattern is one server group spanning both sites.

  • Four StoreFront servers: two per site, one server group. All servers in a group replicate configuration, subscriptions and resource lists to each other, so users see an identical store whichever server (or site) they land on.
  • One shared base URL (e.g., https://storefront.corp.example) fronted by each site’s SF_VIP. Internal DNS resolves the base URL to the local site’s VIP (section 5); remote users reach StoreFront through Gateway.
  • Load balancing with STOREFRONT monitors — the built-in monitor performs a real logon-path check, not just a TCP handshake. Add SOURCEIP persistence so a user’s enumeration and launch stay on one server within a session.
  • Open the group-sync port between sites: StoreFront servers in a group communicate over TCP 808; firewall it across the inter-site link in both directions, or the group will silently split and subscriptions will drift.
  • Keep the Windows tier current: StoreFront servers are Windows servers — patch them in rolling fashion (one at a time, removed from the ADC rotation first). Two servers per site means one can be patched with zero user impact.

8Brokering: Delivery Controllers & zone design

Delivery Controllers

  • Two controllers per site, four in the site overall. Every VDA registers with all controllers listed in its VDA installation; controllers share the brokering load and any one of them can be lost without impact.
  • StoreFront talks to controllers over the XML service (80/443). Point StoreFront at all four controllers (or at an XML load-balancing VIP if you prefer to hide the list).
  • Director runs on the controllers; expose it through the local ADC or an internal FQDN so helpdesk access survives any single server loss.
  • Register controllers on separate hypervisor hosts, and ideally separate shared storage, within each site.

Zones

Create one zone per data centre — Zone A (primary) and Zone B (secondary) — inside the single CVAD site. Zones give you three things:

  • VDA registration locality: VDAs prefer controllers in their own zone, keeping registration traffic and brokering decisions local; they fall back to the other zone automatically if their local controllers disappear.
  • Home-zone user preference: assign users a home zone so launches prefer VDAs in their own data centre — better app latency and less inter-site traffic — while still allowing cross-zone launches when local capacity is full.
  • Local Host Cache boundaries: during a database outage, each zone can keep operating independently against its own controllers’ Local Host Cache (next section).

9Site database: SQL Always On, Local Host Cache and Connection Leasing

The Site database is the one component the whole site genuinely shares. Protect it in two layers: keep it available, and make the estate able to limp along if it is not.

Layer 1 — keep the database available

  • SQL Server Always On availability group with one replica in each DC, synchronous commit, automatic failover, and a listener (or distributed listener) that controllers connect to. Add MultiSubnetFailover=True in the controller connection strings.
  • Latency budget: Citrix controllers are chatty with the database during brokering. Keep controller-to-SQL RTT comfortably under 5 ms, and verify that synchronous-commit write latency added by the AG stays around 1 ms at your inter-site distance. At 2–4 ms metro RTT this is realistic; beyond ~10 ms, reconsider the pattern (use section 2 Pattern B).
  • Backups that are tested: full + log backups of the Site DB, and a documented restore drill performed at least quarterly. An untested backup is a hope, not a design.
  • Maintain the databases (index/stats hygiene) on a schedule; a slow Site DB shows up as slow logons for everyone.

Layer 2 — survive a database outage anyway

  • Local Host Cache (LHC): each controller keeps a local copy of site data. If all controllers lose contact with the SQL replicas simultaneously, existing sessions keep running, and users can connect to already-allocated resources.
  • Connection Leasing (used automatically with LHC): users can reconnect to recently used desktops and published apps during the outage, based on their connection history. New, never-launched resources are the gap — expect degraded-but-alive, not business-as-usual.
  • Design consequence: an SQL failure is an event, not an outage. Staff should still page, but users keep working — that is the correct bar for a brokered desktop estate.
Citrix DaaS variant

With Pattern C (Citrix DaaS), the Site database lives in Citrix Cloud and this section becomes a cloud provider SLA; your equivalent of LHC is the Cloud Connector’s local host cache behavior. Run at least two Cloud Connectors per resource location, on separate hosts, with resilient outbound HTTPS.

10Licensing resilience

VDAs check out licenses when sessions start. If licensing is unreachable, existing sessions keep running and Citrix’s grace period (30 days) covers a prolonged outage — but new launches eventually fail, so design licensing like everything else: redundant, and tested.

  • Preferred: Windows Server Failover Cluster for the License Server role with shared storage, one node per DC, fronted by a clustered FQDN. Failover is automatic and invisible.
  • Alternative: two independent license servers (primary and secondary). Configure VDAs with both servers; they use the primary when reachable. Manually reconcile the license files on both.
  • Back up the license files with the same discipline as the Site database; losing the files during a rebuild is a self-inflicted outage.
  • Monitor license consumption (Citrix ADM / Studio licensing view) and alert at 85–90% so exhaustion never coincides with a failover event.

11Workloads: VDAs, machine catalogs and images in both sites

The edge and control layers only matter because VDAs run sessions. Resilience at this layer is a capacity and locality problem.

  • Machine catalogs exist in both zones for every delivery group that must survive a site loss. A catalog living only in Zone A makes Site B a spectator during a Site A failure.
  • Buffer capacity: plan each site to absorb its own users plus the displaced users from the other site — at reduced comfort if budget demands, but with a written number. A common model: each site sized for 100% of steady-state load, with autoscale absorbing the surge; at minimum, never size below ~65–70% peak utilization per site.
  • Autoscale for pooled catalogs: power-manage idle machines down during the day, keep a warm buffer, and define time/power schemes that react to load spikes during failover.
  • Provisioning: MCS with a master image replicated to both sites (image lifecycle managed in one pipeline so both zones run identical builds). If you use PVS, run a full PVS farm per site with vDisk stores replicated between them — streaming traffic must stay inside its own site; PVS streams do not cross the WAN.
  • Persistent desktops are the awkward case: the VM and its disk live in one site. Protect them with storage replication and treat their RTO as the storage-replication failover time; communicate that their resilience profile differs from pooled sessions.
  • User data: profiles (Citrix UPM or container-based) and home data on storage that is itself replicated or multi-site; a VDA in Site B is useless to a user whose profile store died with Site A.
  • App backends: published apps are only as available as the databases and file servers behind them. Include backend owners in the DR design, or the Citrix estate will “succeed” its failover test while users still cannot work.

Split-brain guardrail

In the full-site-loss row, Site B must be certain Site A is dead before promoting the SQL replica and accepting steering for everything. Two live halves writing to diverged databases is far worse than the outage. Encode the declaration (“who decides, with what evidence”) in the runbook, and make the promotion step manual where automatic failover cannot prove site death.

13Network, latency budget & port plan

Inter-site link requirements

  • Two diverse paths (different fibre routes/providers where possible) with dynamic routing (BGP/OSPF) so a cut cable is a routing event, not a project.
  • Bandwidth sized for: SQL synchronous-commit traffic, StoreFront group sync, ADC health/monitor traffic, cross-zone session launches, plus image/catalog replication bursts. Profile for two weeks before cutting over.
  • Latency budget: keep controller↔SQL and VDA↔controller RTT ≤ 5 ms; at 40 km of metro fibre you have comfortable headroom (fibre adds roughly 0.2 ms per 40 km round trip before equipment latency).
  • QoS: prioritize SQL AG, StoreFront sync and ICA/HDX flows over bulk replication.

14Security hardening notes

  • TLS everywhere: TLS 1.2 minimum (1.3 preferred) on Gateway, StoreFront VIPs and internal XML if you bind it to 443; modern cipher groups; HSTS on user-facing vServers.
  • One SAN certificate per site pair covering the Gateway and StoreFront FQDNs — identical names in both sites keep failover invisible. Track expiry in monitoring; certificate expiry is a classic self-inflicted multi-site outage.
  • MFA on all remote access (nFactor + RADIUS/SAML); consider per-group policies and EPA scans for contractors.
  • ADC management locked down: NSIP only from jump hosts, TACACS+/AD admin auth with least privilege, management-plane rate limiting, and no admin access from the internet.
  • Gateway exposure review: disable legacy ciphers/protocols, enable bot/Rate Limiting protection if licensed, and keep ADC firmware on a supported, patched release — internet-facing ADCs are a frequent attack target.
  • Segmentation: keep the StoreFront/Controller tier in its own VLANs with only the flows from section 13 permitted; VDAs in restricted segments that cannot initiate connections to the management tier.

15Monitoring, operations & DR drills

Monitoring

  • Citrix ADM for the ADC fleet: appliance health, vServer response times, Gateway session counts, certificate expiry, HA state changes.
  • Director for session health: logon duration trends (early warning for StoreFront/SQL trouble), failed logon spikes, machine registration counts per zone.
  • Synthetic logon tests ( scripted Workspace-app logons or equivalent) from each site every few minutes — they detect logon-path failures faster than any component metric.
  • SQL AG health: replica state, synchronization lag and listener reachability on both subnets; alert on anything but SYNCHRONIZED outside a change window.
  • Alert on HA state itself: an ADC pair sitting in active/standby is fine; an unnoticed double failure is not. Every HA failover should page someone.

Operate the design, don’t just own it

Every runbook referenced above should live in the same change system as the firewall rules, with named owners. The most common cause of extended multi-site outages is not a second failure — it is the team losing 45 minutes deciding what the first failure means.

16Final checklist

  • Multi-site pattern chosen (stretched site vs two sites vs DaaS) and rationale recorded
  • ADC HA pair per site: INC, separate failure domains, identical config/firmware, single-node capacity proven
  • GSLB serving one Gateway FQDN; health monitors bound; TTL 60 s; internal DNS routes LAN users to their local StoreFront VIP
  • Gateway: ICA proxy, STAs from both sites registered, Session Reliability and auto-reconnect verified from outside the LAN
  • StoreFront: 4 servers, one group, one base URL, STOREFRONT monitors, TCP 808 open across sites
  • Controllers: 2+ per site; zones per DC; home-zone preferences set; Director reachable after single-server loss
  • SQL Always On: synchronous commit, automatic failover, listener with MultiSubnetFailover, tested backups
  • LHC + Connection Leasing behavior validated in a controlled outage test
  • Licensing redundant (cluster or dual servers) and monitored; license files backed up
  • Catalogs in both zones; each site can absorb the other’s users; autoscale tuned; images identical across sites
  • Port matrix implemented and reviewed by the firewall team; inter-site bandwidth profiled under load
  • Certificates: SAN covering both sites’ FQDNs, expiry monitored
  • Monitoring + synthetic logons live; HA state changes alert
  • Failover matrix printed into runbooks; drills scheduled with named owners
Key takeaway: A resilient two-site Citrix design is a stack of small guarantees — ADC HA at each edge, GSLB steering between sites, redundant StoreFront and controllers, a SQL Always On database with Local Host Cache as the safety net, licensing that survives failover, and machine catalogs with real capacity in both zones. None of it counts until the failure matrix has been rehearsed: run the drills, measure the RTOs, and treat every untested arrow in the diagram as broken by default.
